● Here's a summary of the project and the most recent important changes:

  ---
  Project: SFU Library MCP Server

  An MCP (Model Context Protocol) server that gives Claude access to academic
  research tools, wired to SFU Library databases, OpenAlex, Semantic Scholar,
  and Zotero. The core job is: take a natural-language research query, retrieve,
   embed, rerank, and return the best academic papers — along with citation
  generation, Zotero saving, and access resolution (can SFU students actually
  get this paper?).

  Key modules:
  - openalex.py / semantic_scholar.py — external API clients with budget
  tracking
  - embedding.py / reranker.py — BGE embeddings + CrossEncoder reranking (RRF
  fusion)
  - citations.py, zotero.py, access_resolver.py — downstream tools
  - tools.py — the MCP tool definitions wired to all of the above
  - config.py — server config loaded from env vars

  ---
  Most Recent Important Changes (last 3 commits)

  1. All test failures fixed — suite now 367 passed, 0 failed (5be5a3d)
  A prior refactor surfaced several pre-existing test bugs: a TypeError in
  _openalex_unavailable_reason() when budget was falsy, wrong tool set in a
  DOI-validation test, and _extract_doc_text being called on a raw doc instead
  of a normalized one. All fixed.

  2. Persistent JSONL metrics log (538adb9)
  _record_metric() previously wrote to an in-memory dict that reset on every
  server restart — useless for trend analysis. Now it also appends {ts, tool, 
  latency_ms, success, server_version} to a JSONL file when SFU_METRICS_LOG_PATH
   is set (same pattern as the query log). 12 new tests cover the full
  write/append/failure/bad-path behavior.

  3. Retry + CircuitBreaker on Semantic Scholar (53b1a10)
  S2's free-tier client had no resilience — a single timeout returned None
  silently. It now matches the OpenAlex client: 3 retries with exponential
  backoff, 4x multiplier on 429s (S2's 5-min rate window), and a
  CircuitBreaker(threshold=5, timeout=120s) that opens after 5 consecutive
  failures and probes half-open after the timeout.

  External Data Sources

  openalex.py — Primary search client. Hits the OpenAlex API for academic paper
  retrieval and CrossRef for DOI enrichment. Has two important sub-components:
  - DailyCallTracker — persists today's API call count to disk so the 900
  req/day budget survives server restarts
  - OpenAlexClient — wrapped with retry + circuit breaker; falls back to
  Semantic Scholar if OpenAlex is over budget or its circuit is open

  semantic_scholar.py — Secondary/fallback search client for the S2 Graph API.
  Provides papers, citations, references, and TLDRs. Free tier is ~100 req/5
  min; with API key ~1 req/s. Now has full retry + CircuitBreaker(threshold=5, 
  timeout=120s).

  ---
  Ranking Pipeline

  embedding.py — Loads a sentence-transformer model as a process-level singleton
   (default all-MiniLM-L6-v2, overridable with a fine-tuned checkpoint via
  SFU_EMBEDDING_MODEL_PATH). Provides embed_texts() and cosine similarity
  scoring used by the reranker.

  reranker.py — Two-stage reranking after initial API results come back:
  - Stage 1 (rerank_results): multi-signal scoring — semantic embedding cosine
  (0.35 weight), title token match, recency, fulltext availability, doc type
  match, completeness. Optional RRF fusion with original lexical rank.
  - Stage 2 (rerank_with_crossencoder): CrossEncoder second pass on top-20 Stage
   1 candidates. Feature-flagged off until latency budget is confirmed.
  - Normalizes both PNX (Primo/SFU) and OpenAlex flat doc shapes before scoring.

  ---
  Access & Discovery

  access_resolver.py — Determines the best URL for a paper via a 5-step cascade:
   OpenAlex OA flag → Unpaywall DOI lookup → SFU Database Registry domain match
  → publisher fuzzy match → plain DOI link as last resort. Wraps SFU's EZProxy
  for paywalled subscription content.

  sfu_databases.py — Client for SFU's public Solr-backed database registry
  (databases.lib.sfu.ca). Caches the full registry on disk (24h TTL) and
  provides domain extraction + provider name fuzzy matching so AccessResolver
  can map a publisher to an SFU-licensed database.

  ---
  Citation & Reference Management

  citations.py — Extracts metadata from PNX records and formats it into APA,
  MLA, Chicago, BibTeX, and RIS. Falls back to CrossRef enrichment (via
  openalex.py) when key fields (authors, date, source) are missing.

  zotero.py — Zotero API wrapper. Maps PNX metadata to Zotero item types, saves
  to user library, manages collections, and deduplicates via multi-signal
  matching. Wrapped with a circuit breaker. Fetches valid item types from the
  public Zotero API (24h cache).

  ---
  Infrastructure

  retry.py — Shared CircuitBreaker (CLOSED/OPEN/HALF_OPEN state machine) and
  retry_with_backoff decorator. Works on both sync and async functions. 429
  responses get a 4x backoff multiplier. Used by OpenAlex, Semantic Scholar, and
   Zotero clients.

  cache.py — Thread-safe TTL LRU cache with both a max-entry count and a
  max-memory-MB bound. Used by the API clients to avoid redundant outbound
  calls.

  config.py — All server configuration via env vars + Docker secrets. Defines
  ServerConfig dataclass, load_config(), and validate_config() (returns a list
  of warnings for missing credentials/suboptimal settings). Feature flags like
  rrf_enabled, crossencoder_enabled, query_log_enabled are all here.

  validators.py — Input sanitization: ISBN-10/13 validation, query length
  enforcement, encoding normalization. Guards the MCP tool input boundary.

  formatters.py — Formats raw API results (OpenAlex, Primo PNX, SFU database
  registry) into clean text blocks for Claude to read.

  logging_setup.py — Configures structured logging for the server process.

  ---
  All Active Ranking Systems

  Layer 0 — Upstream Lexical Rankers (external, no control)

  OpenAlex BM25 — When docs arrive from the OpenAlex API they're already ordered
   by OpenAlex's internal relevance ranking, which is BM25-derived (term
  frequency + inverse document frequency over titles, abstracts, concepts). The
  server treats this as the "lexical order" of the result list — position 0 =
  strongest keyword match.

  Primo/SFU BM25 — Same principle for SFU database results. Primo (ExLibris)
  returns docs in its own BM25-derived relevance order. Also becomes the
  "lexical position" input.

  ---
  Layer 1 — Stage 1 Reranker (reranker.py → rerank_results)

  This runs on the upstream results and combines 5–6 signals into a weighted 
  sum:

  ---
  Layer 1b — RRF Fusion (feature-flagged OFF by default)

  When rrf_enabled=True, the semantic_similarity slot is replaced by an RRF
  score instead of raw cosine:

  rrf(d) = 1/(60 + rank_lexical(d))  +  1/(60 + rank_embedding(d))

  This fuses two ranked lists — the original BM25 position from OpenAlex/Primo
  and the embedding cosine rank — normalized to [0,1] and dropped into the same
  0.35-weight slot. The benefit is that neither ranker can fully suppress a doc
  the other rates highly; it rescues queries where one signal is blind.

  ---
  Layer 2 — CrossEncoder Second Pass (feature-flagged OFF by default)

  When crossencoder_enabled=True, the top-20 Stage 1 results get re-scored by
  cross-encoder/ms-marco-MiniLM-L-6-v2. Unlike the bi-encoder (which embeds
  query and doc independently), a cross-encoder takes (query, doc) as a single
  input and scores interaction effects between them. More accurate but ~50–100ms
   latency on CPU, which is why it's gated.

● This is worth thinking through carefully. Short answer: yes, but the practical
   path is self-hosting OpenAlex's own data dump, not replacing it with 
  something else.

  Here's why:

  OpenAlex publishes their full dataset under CC0 — ~250M works as Parquet
  snapshots on AWS S3, updated weekly. You could download the snapshots, index
  them into a local Elasticsearch or OpenSearch cluster, and run unlimited
  queries against your own instance. It's the same data, zero API rate limits,
  and no daily budget tracking needed.

  The tradeoff is real though:
  - The full snapshot is ~500GB+ compressed (multi-TB uncompressed) —
  significant storage and indexing infra
  - You'd own the update cadence — weekly re-sync jobs to stay fresh
  - Search relevance would be your problem: OpenAlex's hosted API gives you
  their BM25 tuning; a bare Elasticsearch index gives you vanilla BM25 with
  whatever mappings you configure

  True third-party alternatives are weaker:

  ┌────────────────────┬──────────────────────┬─────────────────────────────┐
  │       Option       │       Strength       │       Gap vs OpenAlex       │
  ├────────────────────┼──────────────────────┼─────────────────────────────┤
  │ Semantic Scholar   │ 200M+ papers, TLDRs, │ Already used as fallback;   │
  │ (already have it)  │  citation graph      │ same API rate constraints   │
  ├────────────────────┼──────────────────────┼─────────────────────────────┤
  │ CORE               │ OA-only, good        │ ~50M works, no citation     │
  │                    │ fulltext             │ counts                      │
  ├────────────────────┼──────────────────────┼─────────────────────────────┤
  │ PubMed local dump  │ Best for biomedical  │ Biomedical only, no         │
  │                    │                      │ citation graph              │
  ├────────────────────┼──────────────────────┼─────────────────────────────┤
  │ CrossRef local     │ DOI metadata         │ No abstracts, no semantic   │
  │                    │                      │ search                      │
  ├────────────────────┼──────────────────────┼─────────────────────────────┤
  │ DBLP               │ CS literature        │ CS only                     │
  └────────────────────┴──────────────────────┴─────────────────────────────┘

❯ is open alexes BM25 open source to see if there are any bottle necks or

● Short answer: No — OpenAlex's search layer is not open source, but it's built 
  on Elasticsearch, which is.

  Here's the breakdown:

  What is open:
  - Their data (CC0 snapshots on S3) — fully open
  - The BM25 algorithm itself — Elasticsearch uses Okapi BM25 as its default
  similarity function since v5.0, and OpenSearch (the Apache 2.0 fork) has the
  full implementation visible
  - Some of their data pipeline code is on GitHub (ourresearch/openalex-guts)
  but it's the ETL/enrichment layer, not the search layer

  What is not open:
  - Their API/search service — closed, hosted-only
  - Their specific Elasticsearch field mappings, query construction, and BM25 
  tuning parameters (k1, b, field boosts per field like title vs. abstract vs.
  concepts) — unpublished
  - How they weight concept tags, institution signals, citation counts in
  relevance — unknown

  What this means practically:

  You can't inspect or fork their BM25 config. But since it's Elasticsearch
  under the hood, if you self-hosted the snapshot you'd have more control than
  you do now, not less — you could tune:
  - k1 (term frequency saturation) and b (field length normalization)
  - Per-field boost weights (title vs. abstract vs. author vs. concept tags)
  - Custom analyzers (stemming, synonyms for academic jargon)
  - Query-time boosting by citation count or recency

  The actual bottleneck in the current setup isn't BM25 tuning though — it's
  that the upstream lexical rank from OpenAlex is a black box that the reranker
  then tries to correct. The reranker's title token overlap signal
  (title_relevance at 0.15 weight) is essentially a crude BM25 approximation
  applied after the fact to compensate for not controlling the upstream query.

  If you self-hosted on OpenSearch, you'd close that loop — the reranker's title
   signal could be replaced by a properly tuned upstream BM25 query you control
  directly. That's the real architectural win, more than the rate limit removal.

  Want me to look at how the current OpenAlex query is actually constructed in
  openalex.py to see what fields it's hitting and where tuning headroom might
  exist even within the current API?

● This is the core architectural tension worth getting right before building
  anything. Let me think through the options clearly.

  ---
  The Fundamental Split

  Your data freshness concern and your ranking control concern are actually two 
  independent problems that don't need the same solution:

  Data freshness  →  WHERE the documents come from
  Ranking quality →  HOW you score and order them

  You can solve ranking without touching data freshness, and vice versa. The
  question is which combination makes sense.

  ---
  Three Architectures

  Option A — Over-fetch + Local Pipeline (least infra, solvable now)

  Keep OpenAlex as the live data source. Never replace it. But instead of taking
   their top 10, request their top 50–100, then run your own BM25 + reranker on
  those candidates.

  Live OpenAlex API (fresh, authoritative) → top 100 raw results
          ↓
  Your local BM25 re-scores those 100 (title/abstract field boosts you control)
          ↓
  Your reranker (embedding + CrossEncoder)
          ↓
  Top 10 served

  What you gain: Full ranking control, always fresh data, no snapshot needed, no
   staleness problem.
  What you lose: You still can't control which 100 OpenAlex gives you — their
  upstream BM25 determines the candidate pool. If the right paper isn't in their
   top 100, you never see it.
  Infra cost: Zero new infra. This is a code change to openalex.py.

  ---
  Option B — OpenSearch as Cache + Weekly Diff Sync

  Self-host OpenSearch, seed it from OpenAlex snapshots, apply OpenAlex's weekly
   diff updates via a cron job. Your pipeline queries OpenSearch exclusively.

  OpenAlex weekly diff (cron job) → OpenSearch local index (always ≤7 days

  ---
  Option C — Federated Hybrid (solves the "muddling" problem directly)

  This is the architecture that answers your exact concern. Two separate
  indexes, clear priority rules, no muddling:

  Query comes in
      │
      ├──► Live OpenAlex API  (papers < 30 days old, or when local misses)
      │         fresh, authoritative, rate-limited
      │
      └──► Local OpenSearch   (papers > 30 days old, your enriched corpus)
                stale-safe zone, no rate limits, fully tunable

      Both result sets fed into the same reranker
      Deduplication by DOI before ranking
      Source tag attached to each result (for debugging)

  What you gain: Fresh papers always come from live API, older papers come from
  your tunable local index, the reranker doesn't care which source a doc came
  from.
  What this avoids: Your local stale data never competes with fresh results on
  the same paper — if a DOI exists in both, you deduplicate and keep the
  freshest version.
  Infra cost: OpenSearch container + the incremental index-as-you-search
  approach (no snapshot needed to start).

  ---
  The "Muddling" Answer Directly

  The muddling problem you described — local stale data mixing with fresh API
  results — only happens if you merge two result sets for the same query without
   deduplication. The fix is simple:

  # Route by age, not by query
  if result["date"] > thirty_days_ago:
      source = "live_api"   # authoritative for new papers
  else:
      source = "local_index"  # authoritative for established literature

  Or more robustly: always query both, deduplicate by DOI keeping the freshest
  version, then rank the merged set. Your local corpus enriches the candidate
  pool for established literature; the live API covers everything recent.
  Neither muddies the other because DOI deduplication is the separator.

  2. Alternatives to BM25 Worth Evaluating

  Yes, and one in particular is very relevant to your use case:

  SPLADE (Sparse Lexical and Expansion Model)
  Probably the most interesting upgrade from vanilla BM25 for academic text.
  It's a learned sparse retrieval model — it works in the same inverted index
  paradigm as BM25 (so OpenSearch can serve it) but instead of term frequency,
  it uses a BERT-like encoder to learn which terms are important and expands
  queries with semantically related terms automatically.

  On academic benchmarks (BEIR, TREC-COVID, NFCorpus) SPLADE consistently
  outperforms BM25 by 10–20% nDCG. It would directly replace BM25 in your
  OpenSearch index and remove the need for the title_relevance heuristic in your
   reranker entirely.
